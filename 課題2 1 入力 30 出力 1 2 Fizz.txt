課題2-5

1. XSS（クロスサイトスクリプティング）
攻撃方法
XSS（Cross-Site Scripting）は、Webページに悪意のあるスクリプトを実行させる攻撃である。

例えば、ユーザーが入力した文字列をHTMLにそのまま埋め込むWebサイトがあるとする。入力値が適切にエスケープされていない場合、攻撃者がHTMLやJavaScriptを入力することで、それが他のユーザーのブラウザ上で実行される可能性がある。

攻撃例
例えば、コメント欄に次のような文字列が入力されたとする。

<script>alert("XSS")</script>

Webサーバがこの文字列をエスケープせずにHTMLとして表示すると、ブラウザはscriptタグをHTMLとして解釈し、JavaScriptを実行する。

実際の攻撃では、Cookieなどの情報を不正に取得したり、偽の入力フォームを表示したりするなど、より深刻な被害につながる可能性がある。

対策
ユーザーから受け取った文字列をHTMLに出力するときはHTMLエスケープを行う。

Rubyでは CGI.escapeHTML などを利用する。

HTML、JavaScript、URLなど、それぞれの出力先に適したエスケープを行う。

Content Security Policy（CSP）などのセキュリティ機能も利用する。

2. CSRF（クロスサイトリクエストフォージェリ）
攻撃方法
CSRF（Cross-Site Request Forgery）は、ユーザーがログインしているWebサービスに対して、ユーザーが意図していないリクエストを送信させる攻撃である。

例えば、ユーザーがあるWebサービスにログインしている状態で、攻撃者が用意したWebページを開いたとする。そのページから対象サービスにリクエストが送られると、ブラウザがログイン情報に関連するCookieを自動的に送信する場合がある。

その結果、ユーザー本人が操作したようにサーバがリクエストを処理してしまう可能性がある。

対策
CSRFトークンを使用する。

状態を変更する処理では、単純なGETリクエストを使用しない。

Cookieに SameSite 属性を適切に設定する。

Origin や Referer ヘッダを必要に応じて確認する。

フレームワークが提供するCSRF対策機能を利用する。

3. XSS・CSRF以外のセキュリティ問題：SQLインジェクション
攻撃方法
SQLインジェクションは、ユーザーから入力された文字列をSQL文に直接連結することで、意図しないSQL文を実行させる攻撃である。

例えば、次のように入力値をSQL文に直接連結するプログラムがあるとする。

sql = "SELECT * FROM users WHERE name = '#{name}'"

このようなコードでは、入力された文字列によってSQL文の構造そのものが変化する可能性がある。

攻撃例
例えば、ログインフォームのユーザー名にSQL文の構造を変更するような特殊な入力を与えると、本来想定していなかった条件でSQLが実行される可能性がある。

その結果、認証を回避されたり、データベース内の情報を不正に取得・変更されたりする危険がある。

対策
SQL文にユーザー入力を文字列連結で直接埋め込まない。

プレースホルダを使用したパラメータ化クエリを利用する。

ORMなどの安全なデータベースアクセス機能を利用する。

データベースユーザーの権限を必要最小限にする。

入力値の形式や長さを適切に検証する。

課題3-1
基本課題3-1 NoSQL
1. MongoDBとは

MongoDBはNoSQLに分類されるデータベース管理システムの一つである。RDBMS（リレーショナルデータベース管理システム）では、データをテーブルと呼ばれる表形式で管理する。一方、MongoDBではデータをJSONに似たドキュメント形式で保存する。

MongoDBでは、データベースの中に「コレクション」があり、その中に複数の「ドキュメント」を保存する。RDBMSのテーブルとレコードに近い構造であるが、MongoDBではドキュメントごとに異なる構造を持たせることもできる。

例えば、ユーザー情報を保存する場合、次のようなデータを扱うことができる。

{
  "name": "Taro",
  "age": 20,
  "email": "taro@example.com"
}


このように、MongoDBはデータを柔軟な形式で保存できることが特徴である。

2. RDBMSと比較した長所

MongoDBの長所の一つは、データ構造を柔軟に変更できることである。RDBMSでは基本的にテーブルの構造をあらかじめ決める必要がある。一方、MongoDBではドキュメントごとに異なる項目を持たせることができる。

また、大量のデータを複数のサーバに分散して処理することにも向いている。データを複数のサーバに分散させることで、アクセスが多いシステムでも処理を分散できる。

さらに、JSONに近い形式でデータを扱うため、Webアプリケーションなどで利用しやすい。プログラムで扱うオブジェクトとデータベース上のデータの対応も比較的分かりやすい。

3. RDBMSと比較した短所

一方で、MongoDBはRDBMSと比較して、複雑なリレーションを扱う処理が苦手な場合がある。

RDBMSでは複数のテーブルをJOINして関連するデータを取得することができる。MongoDBにも関連データを扱う機能はあるが、複雑な関係を持つデータでは、RDBMSの方が扱いやすい場合がある。

また、データの整合性を厳密に管理する必要があるシステムでは、RDBMSの方が適している場合がある。そのため、どのようなシステムでもMongoDBがRDBMSより優れているわけではなく、データの性質やシステムの目的によって使い分ける必要がある。

4. 想定している用途

MongoDBは、データ構造が頻繁に変化するWebサービスや、大量のデータを扱うシステムなどで利用される。

例えば、Webサイトのユーザー情報、商品情報、ログデータ、コンテンツ管理などに利用できる。

特に、保存するデータの項目が一定ではない場合や、データ量が非常に多い場合に適している。

5. 実際の使用例

MongoDBはWebサービスや企業のシステムなどで利用されている。例えば、ユーザー情報や商品情報など、比較的柔軟な構造を持つデータを保存するために利用できる。

また、アクセスログやセンサーデータなど、大量に発生するデータを保存する用途にも利用されている。

6. まとめ

MongoDBは、ドキュメント形式でデータを保存する代表的なNoSQLデータベースである。

RDBMSと比較すると、データ構造を柔軟に変更でき、大量のデータを扱いやすいという長所がある。一方、複雑なリレーションや厳密なデータ整合性が必要な場合には、RDBMSの方が適している場合がある。

したがって、MongoDBとRDBMSはどちらか一方が常に優れているのではなく、扱うデータやシステムの目的に応じて選択することが重要である。

課題3-2
基本課題3-2 セキュリティ
1. SQLインジェクションとは

SQLインジェクションとは、Webアプリケーションやプログラムへの入力を利用して、開発者が意図していないSQL文を実行させる攻撃方法である。

ユーザーから受け取った文字列をSQL文に直接連結している場合に発生しやすい。

SQLインジェクションが成功すると、本来許可されていないデータの取得、変更、削除などを実行される可能性がある。そのため、データベースを利用するシステムでは重要なセキュリティ上の問題となる。

2. 攻撃方法

今回のweak sqlite.rbでは、次の部分に問題がある。

str = "UPDATE students SET name = \"#{new_name}\" WHERE student_id = #{id}"


id と new_name は標準入力から取得している。その値をチェックせず、そのままSQL文に埋め込んでいる。

例えば通常、

1,Taro


と入力すると、

UPDATE students SET name = "Taro" WHERE student_id = 1


が実行される。

しかし、入力にSQLの構文を含めることで、プログラムが作成するSQL文を意図しない形に変更できる。

例えば、名前の入力に引用符などのSQL構文を含めることで、元々プログラムが用意した文字列の外にSQL文を追加できる可能性がある。

このように、入力値をSQL文の一部として直接扱っていることがSQLインジェクションの原因となる。

3. weak sqlite.rbへの攻撃例

例えば、通常の入力として、

1,Taro


を入力すると、

UPDATE students SET name = "Taro" WHERE student_id = 1


となる。

一方、入力値にSQL構文を含めると、プログラムが想定していないSQL文を生成できる場合がある。

例えば、入力値として引用符やSQLの条件式などを含めることで、WHERE 条件を変更したり、複数のSQL文を実行できる可能性がある。

このプログラムでは execute_batch を使用しているため、入力値によってSQL文を追加できる構造になっている点も危険である。

実際の攻撃では、データの内容を変更するだけでなく、データを削除したり、データベースの情報を取得したりする攻撃につながる可能性がある。

4. 対策

SQLインジェクションへの代表的な対策は、SQL文とユーザーから入力された値を分離することである。

SQLite3では、プレースホルダを使用することができる。

例えば、次のように変更する。

# coding: utf-8
require 'sqlite3'

db = SQLite3::Database.new("sandbox.db")

id, new_name = gets.chomp.split(",")

sql = "UPDATE students SET name = ? WHERE student_id = ?"

db.execute(sql, new_name, id)

db.close


この方法では、ユーザーが入力した値がSQL文そのものとして解釈されにくくなる。

つまり、

"UPDATE students SET name = \"#{new_name}\" WHERE student_id = #{id}"


のように文字列を直接連結するのではなく、

"UPDATE students SET name = ? WHERE student_id = ?"


として、値を別の引数として渡す。

このような方法をプリペアドステートメントやプレースホルダと呼ぶ。

5. まとめ

SQLインジェクションは、ユーザーから受け取った入力をSQL文に直接組み込むことで発生する攻撃である。

今回のweak sqlite.rbでは、id と new_name をSQL文に直接埋め込んでいることが問題である。

対策として、SQLite3のプレースホルダを使用し、SQL文と入力値を分離することが重要である。

また、入力値の検証や、データベースユーザーに必要以上の権限を与えないことなども、セキュリティ対策として重要である。

応用課題3-1 データベース操作（Web版）
1. 概要

基本課題3-4で作成したデータベース検索機能を、Webサーバから利用できるようにした。

WebサーバにはRubyのWEBrickを使用し、データベースにはSQLiteを使用した。

lab.db に保存されている labs テーブルと lab_members テーブルを検索し、ブラウザ上に検索結果を表示する。

2. 実装した機能
研究室名からメンバーを検索

以下のリクエストを受け付ける。

http://127.0.0.1:2000/lab_search?lab_name=hci-lab


入力された研究室名を labs テーブルから検索し、研究室の id を取得する。

その後、取得した id と lab_members テーブルの lab_id を利用して、その研究室に所属するメンバーを検索する。

研究室名の検索では、データベースから id と lab_name を取得し、Ruby側で入力された研究室名と比較するようにした。

メンバー名から他のメンバーを検索

以下のリクエストを受け付ける。

http://127.0.0.1:2000/member_search?member_name=Daisuke%20Sakamoto


入力されたメンバー名を lab_members テーブルから検索し、そのメンバーの lab_id を取得する。

その後、同じ lab_id を持つメンバーを検索する。

検索結果には、入力された本人が含まれないようにRuby側で比較して除外した。

3. SQLについて

研究室名からメンバーを検索する処理では、まず以下のSQLを使用して labs テーブルから研究室のIDと名前を取得した。

SELECT id, lab_name FROM labs


取得したデータをRuby側で比較し、入力された研究室名と一致した場合、その研究室の id を取得する。

その後、以下のSQLを使用して、取得した lab_id と一致するメンバーを検索した。

SELECT member_name
FROM lab_members
WHERE lab_id = ?


? の部分には、先ほど取得した lab_id が入る。

メンバー名から検索する処理では、以下のSQLを使用して lab_members テーブルから lab_id と member_name を取得した。

SELECT lab_id, member_name FROM lab_members


取得したデータをRuby側で比較し、入力されたメンバー名と一致するデータから lab_id を取得する。

その後、以下のSQLで同じ研究室に所属するメンバーを検索した。

SELECT member_name
FROM lab_members
WHERE lab_id = ?


取得したメンバーの名前と入力された名前をRuby側で比較し、入力された本人を結果から除外した。

SQLに値を直接文字列連結するのではなく、? のプレースホルダを使用して値を渡すことで、安全にSQLを実行できるようにした。

4. 実行結果

サーバを以下のコマンドで起動した。

$ ruby labSearchServer.rb


ブラウザから以下のURLへアクセスした。

http://127.0.0.1:2000/lab_search?lab_name=hci-lab


その結果、hci-lab に所属するメンバーの一覧がブラウザに表示された。

また、以下のURLへアクセスした。

http://127.0.0.1:2000/member_search?member_name=Daisuke%20Sakamoto


その結果、Daisuke Sakamoto と同じ研究室に所属する他のメンバーがブラウザに表示された。

5. 考察

WEBrickを利用することで、基本課題3-4で作成したRubyとSQLiteによるデータベース検索処理を、Webブラウザから利用できるようになった。

lab_search では、研究室名から研究室のIDを取得し、そのIDを利用して所属するメンバーを検索した。

member_search では、メンバー名から所属する研究室のIDを取得し、その研究室に所属する他のメンバーを検索した。

また、SQLに値を直接文字列として連結するのではなく、プレースホルダを使用して値を渡すことで、入力値がSQL文の一部として解釈されることを防ぐようにした。

今回の実装では、検索条件の一部をRuby側で比較する方法も使用した。これにより、今回使用している lab.db のデータに合わせて、研究室名やメンバー名を検索できるようにした。
